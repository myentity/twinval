# twinval

**A multi-level psychometric validation framework for LLM-based "digital twins" of human questionnaire respondents.**

`twinval` answers one question at several levels of aggregation: *how faithfully does a twin (here: a GPT-5 persona of a real
respondent) reproduce the answers of its human?* Fidelity is **not treated as a single property**. The framework separates

| level | unit | what is tested |
|---|---|---|
| 1 Profile | respondent | can the twin of person *i* be told apart from the twins of other people (identification)? how close are the profiles (CCC, MAE/RMSE, bias)? |
| 2 Scale | scale | individuation (Pearson r, AUC), calibration/agreement (CCC = r x C_b), cross-validated recalibration, reliability-corrected r |
| 3 Structure | scale / instrument | paired ordinal CFA: estimability, absolute fit and measurement invariance kept apart (Wu-Estabrook primary; Millsap-Tein/Liu as sensitivity), ESEM with target rotation, Procrustes + Tucker's phi, admissibility gate |
| 4 Item | item | agreement and error, bias and variance compression, ANOVA-style variance decomposition, link with loading discrepancy |
| 5 Synthesis | scale | cross-level associations (cluster bootstrap) and a rule-based typology of scales; **no single integrated score** |

This is the companion code for the article **"A Multilevel Framework for Evaluating the Fidelity of LLM-Based Digital
Twins"** (N = 484 human-twin pairs). Its purpose is to give researchers a reusable, pre-registrable pipeline for asking,
at five distinct levels of aggregation (profile, scale, structure, item, cross-level synthesis), how faithfully an
LLM-based digital twin reproduces the person it is meant to represent - instead of collapsing that question into one
overall accuracy score, which the framework deliberately avoids (see the Synthesis row above).

## Installation

```bash
git clone https://github.com/myentity/digital-twin-fidelity-framework.git
cd digital-twin-fidelity-framework
pip install -e .            # Python >= 3.10: numpy, pandas, scipy, statsmodels, scikit-learn, matplotlib, pyyaml
twinval check-r             # optional: Rscript + lavaan + semTools (needed for the structural level only)
```

The R backend is **optional**. Without it, levels 1, 2 and 4 and the scale-level part of level 5 run normally; the
structural level (CFA, ESEM, Tucker's phi) and everything that depends on it (typology, loading discrepancy) is skipped
with an explicit note in `report.md`. Install R packages with `install.packages(c("lavaan", "semTools"))`.

## Quick start

```bash
# 1. check the data files
twinval validate --data examples/data

# 2. smoke run (small resampling sizes; about 4 minutes with R, seconds without)
twinval run --data examples/data --out results/example --fast

# 3. a "real" run with the settings of the study (5000 bootstrap replicates etc.)
twinval run --data examples/data --out results/example_full --config configs/example.yaml

# a subset of stages
twinval run --data examples/data --out results/example --stages audit,profile,scale,item
```

Python API:

```python
import numpy as np
from twinval import load_config, load_study
from twinval import scale, profile

cfg = load_config(overrides={"scale": {"n_boot": 1000}})
study = load_study("examples/data")            # complete-case paired data, scale scores, item arrays
rng = np.random.default_rng(1)
core = scale.core_table(study, cfg, rng)       # r, AUC, CCC, C_b with bootstrap CIs, one row per scale
```

CLI reference: `twinval run|validate|scale-key|check-r|write-config` (`twinval <cmd> -h`).

## Input data

### 1. Paired data files (one file per scale or sub-scale)

```
<data_dir>/<scale_id>_paired_wide.csv        e.g.  examples/data/148_Conscientiousness_paired_wide.csv
```

| column | meaning |
|---|---|
| `ID` | respondent identifier, **the same in every file of a study** (any string/number; used only for alignment) |
| `it1_h` ... `itK_h` | answer of the **human** to the 1st ... K-th item of the scale |
| `it1_t` ... `itK_t` | answer of the **twin of the same human** to the same items |

Rules (checked by `twinval validate`; violations raise a `DataError` with the file name):

* **integer response categories**, already **reverse-scored** where the item is reverse-keyed;
* `itk` follows the item order of the scale in the registry (see the key below); K must equal the registry item count;
* the response range must lie inside the instrument range of the registry (e.g. 1-5);
* one row per respondent; respondents that are missing or incomplete in any loaded file are dropped (complete-case across
  all files; the number is logged);
* the file name is `<scale_id>_paired_wide.csv` (also accepted: `<legacy_id>_paired_wide.csv`, the original file names).

A scale that is a *sub-scale of another one* (BFI-2 facets inside domains) has its own file with the subset of items; all
files are consistent because the paired answers are the same numbers. Instruments are picked up automatically for every
scale file that is found; missing files are reported and skipped.

### 2. The registry = scale key (`src/twinval/registry/instruments.yaml`)

The registry links files, items, scoring and redundancy rules. Per instrument: `key`, `name_en`, `item_prefix`, response range,
and a list of `scales`; per scale:

```yaml
- id: 148_Conscientiousness        # -> file name 148_Conscientiousness_paired_wide.csv
  name_en: Conscientiousness
  name_ru: Добросовестность
  legacy_id: 148_Добросовестность    # original file stem
  level: domain                    # scale | subscale | domain | facet | total
  scoring: mean                    # how the scale score is built from the items: mean | sum
  items: [BFI2_3, BFI2_8, ...]     # canonical item codes, in the order of it1..itK
  reverse_items: [BFI2_8, ...]     # reverse-keyed items (for the reverse-keyed analysis)
  parent: null                     # facets point to their domain
  redundant: false                 # true for facets and total scores (see below)
```

**Redundancy rule.** A facet is a subset of the items of its domain and a total score is the sum of the sub-scales. They are
analysed at the scale level, but excluded from the profile (60 non-redundant scales), from ESEM and from the item level,
because they would count the same items twice (and make the joint factor model unidentified).

The packaged registry contains only the two example instruments. To analyse **your own instruments**, write a registry in the same
format (copy the entries of BFI-2 / SPH as a template, give each instrument a numeric id), put the data files named by your
`scale_id`s into a folder and pass `--registry my_instruments.yaml --data my_data/`. Nothing else in the code is instrument-specific.

### 3. Scale key of the example instruments

The same key for the packaged registry is in [`docs/SCALE_KEY.md`](docs/SCALE_KEY.md) (`twinval scale-key`).

## Configuration

All thresholds and resampling sizes live in one YAML file; the defaults reproduce the study
([`src/twinval/configs/default.yaml`](src/twinval/configs/default.yaml), `twinval write-config --out my.yaml`).
Key settings:

| block | key | default | meaning |
|---|---|---|---|
| thresholds | `r_practical` / `auc_ci_low` | 0.50 / 0.50 | practically adequate individuation: r >= 0.50 **and** lower AUC CI > 0.50 |
| thresholds | `cb_adequate` | 0.80 | adequate calibration: C_b >= 0.80 |
| thresholds | `phi_congruence` | 0.85 | Tucker's phi >= 0.85 = congruence |
| thresholds | `bootstrap_valid_min` | 0.80 | Tucker CI is stable if >= 80% of bootstrap fits are admissible |
| thresholds | `cfa_delta_cfi_min` / `cfa_delta_rmsea_max` | -0.010 / 0.015 | invariance step supported only if delta CFI >= -0.010 and delta RMSEA <= 0.015 ... |
| thresholds | `cfa_delta_srmr_loadings_max` / `cfa_delta_srmr_thresholds_max` | 0.030 / 0.010 | ... and delta SRMR below these limits (loading / threshold-intercept steps) |
| thresholds | `cfa_srmr_fit_max` | 0.08 | absolute fit of the baseline CFA supported if SRMR <= 0.08 (operational criterion; sensitivity 0.05) |
| thresholds | `cfa_pd_tolerance`, `cfa_bound_tolerance` | 1e-6 | tolerances of the positive-definiteness and |r| <= 1 checks |
| thresholds | `near_boundary_loading`, `near_boundary_correlation` | 0.95 | warning flags for standardised estimates close to the boundary |
| profile / scale / item | `n_boot`, `n_perm`, `cv_repeats`, ... | 5000 / 2000 / 10 | resampling sizes |
| item | `data_version` | `raw` | `raw` (original categories, the study's primary analysis) or `harmonized` (sensitivity analysis), see [Caveats](#caveats) |
| structural | `order_check_permutations` | 0 | refit non-clean CFA models on this many random row orders and flag order-sensitive verdicts (see [Caveats](#caveats)) |
| structural | `n_boot_tucker` | 500 | Tucker bootstrap (about 15 s per replicate for the two example instruments) |
| structural | `primary_branch` | `wu` | `millsap`: Millsap/Liu sequence as the primary branch (sensitivity) |
| structural | `use_delta_srmr`, `exclude_near_boundary`, `structural_priority` | `true`, `false`, `cfa` | sensitivity switches: drop delta SRMR; treat near-boundary models as not usable; let ESEM decide before CFA |
| synthesis | `type_labels` | see typology | names of the scale types |

Everything is deterministic given `run.seed`; every stage derives its own generator from it. `run_manifest.json`
records package versions, R/lavaan versions, seed, config hash and timings of each run.

### Data versions (raw vs harmonised)

The **input** files are always the raw answers. Harmonisation (symmetric merging of adjacent response categories when
Human and Twin use different category sets for an item, e.g. the twin never answers "1") is an internal step
(`prep.harmonize`); the harmonised data are written to `00_audit/harmonized_data/` in exactly the input format
(`ID, it1_h..itK_h, it1_t..itK_t`; merged categories are re-numbered 1..k'), and every merge is listed in `harmonization_log.csv`.

| level | data used |
|---|---|
| profile, scale | **raw** input answers (scale scores from the original items) |
| structural (CFA, ESEM, Tucker) | **harmonised** (always) |
| item | **raw** by default (the study's primary analysis); `item.data_version: harmonized` is a sensitivity analysis |

The item tables carry a `data_version` column, `report.md` has a "Data versions" section and `run_manifest.json` records
`data_versions`.

Column dictionary of the main tables: [`docs/OUTPUTS.md`](docs/OUTPUTS.md). The two tables to start with:
`cross_level_results_matrix.csv` (one row per main result of every level, units are never mixed) and `scale_typology.csv`
(one row per scale with the three axes, the final type and the reason).

## The typology

Every scale is assigned to one type by explicit, pre-specified rules on three axes (no clustering, no post-hoc thresholds):
**I** individuation, **C** calibration, **S** structural status. Analysis statuses without structural evidence are assigned first, then the types A-E in this order; the first match wins:

| Type | Short label | I | C | S | Rule |
|---|---|---|---|---|---|
| - | Structural evidence not established (baseline CFA misfit) | | | `cfa_misfit` | admissible baseline CFA, SRMR > .08, no admissible paired ESEM |
| - | Structural evidence not established (baseline fit not testable) | | | `cfa_fit_not_testable` | just-identified baseline (df = 0) and no supported later step, no admissible paired ESEM |
| - | Structural model not estimable | | | `model_not_estimable` | CFA (and ESEM, where applicable) fitted but nonconverged, not identified or inadmissible |
| - | Structural analysis not conducted / not applicable | | | `not_tested` | no structural model fitted |
| A | Score fidelity with measurement-invariance support | + | + | scalar or metric | r >= .50 and lower AUC CI > .50; C_b >= .80; metric or scalar invariance |
| B | Individuation without adequate calibration | + | - | any structural evidence | practically adequate individuation and C_b < .80 |
| C | Limited individuation with structural evidence | - | +/- | scalar, metric, configural fit or congruence | individuation not established, structural evidence exists |
| D | Score fidelity with structural discrepancy | + | + | discrepant | I and C adequate; no CFA conclusion; admissible paired ESEM with phi < .85 |
| E | Score fidelity with limited structural evidence | + | + | configural fit or congruence | I and C adequate; metric/scalar not established, but configural fit or ESEM congruence |
| F | Unclassified residual | | | | everything else (e.g. discrepant structure without adequate individuation) |

**Structural status (S)** keeps three properties apart (details in [`docs/METHODS.md`](docs/METHODS.md)):
*estimability* of every CFA model (nonconverged / identification not established / inadmissible / admissible; estimates near
the boundary are warnings, not exclusions), *absolute fit* of the baseline model (SRMR <= .08; df = 0 is "not testable", not
"failed") and *invariance* step by step along the Wu-Estabrook sequence (delta CFI, delta RMSEA and delta SRMR; a step whose
models are not admissible is "not evaluable", never "rejected"). S is the first match of `scalar_invariance` >
`metric_invariance` > `configural_fit` (CFA conclusion from an admissible, well-fitting baseline) > `congruence_supported` /
`structurally_discrepant` (only if the CFA gives no conclusion **and** both ESEM solutions are admissible) > `cfa_misfit` /
`cfa_fit_not_testable` / `model_not_estimable` > `not_tested`. Formal CFA evidence outranks the descriptive ESEM/Tucker
evidence, and a Tucker's phi from an inadmissible ESEM never makes a scale "congruent" or "discrepant".

Flags never change a type; they are listed in `structural_flags` and summarised in `evidence_quality`:
`identification_scheme_sensitive` (the evaluated Millsap/Liu and Wu loading tests disagree), `identification_route_dependent` (Wu does not interpret its loading step after a rejected threshold step, Millsap/Liu supports loadings), `near_boundary_*`,
`conflicting_fit_diagnostics`, `threshold_supported`, `baseline_fit_not_testable`, `baseline_not_identified`,
`invariance_supported_under_baseline_misfit`, `cfa_esem_conflict`, `bootstrap_unstable`, `order_sensitive`.

## Methods map

| Procedure | Module | Key functions |
|---|---|---|
| Human-based z, CCC = r x C_b, bootstraps, BH, bootstrap p with (b+1)/(B+1) | `stats.py` | `human_z`, `ccc_components`, `cluster_bootstrap_spearman` |
| Category harmonisation (symmetric adjacent merge), item batteries, ESEM targets | `prep.py` | `harmonize`, `item_battery` |
| Own-twin identification (equal-weight RMS distance, full/distinctive), permutation, robustness, leave-one-instrument-out | `profile.py` | `identification` |
| Profile CCC/MAE/RMSE/bias in the identification specification, Mahalanobis, mean-profile Procrustes | `profile.py` | `calibration`, `mahalanobis_and_mean_profile` |
| Scale r, AUC (permutation), CCC/C_b | `scale.py` | `core_table` |
| CV recalibration (location-scale vs OLS), nested leakage-free bootstrap | `scale.py` | `recalibration` |
| Reliability-corrected r (alpha, Spearman-Brown, CR) | `scale.py` | `disattenuation` |

`tests/test_reference_paper.py` checks that, for the two example instruments, the framework reproduces the values of the
original study: scale-level r/CCC/C_b (to 1e-3), item-level metrics and variance decomposition (to 1e-6), Tucker's phi (to

### Synthetic demonstration: every kind of result

Two real instruments cannot show all outcomes (no cluster bootstrap, no leave-one-instrument-out, only some types).
`twinval simulate` generates **fictional instruments with a twin of known behaviour** (weak individuation, shifted and
compressed answers, unequal loadings, repeated answers, ...). The committed example [`examples/synthetic`](examples/synthetic)
has 10 instruments / 29 scales / 500 respondents and yields **all eight typology outcomes** (A-F, CFA misfit, model not
estimable); its results are in [`examples/synthetic/results`](examples/synthetic/results) and the designed-versus-recovered
types in `expected_vs_recovered.csv`. See [`docs/SYNTHETIC.md`](docs/SYNTHETIC.md) for the generative model, all parameters and
the caveats (borderline CFA convergence).

```bash
twinval simulate --scenario examples/synthetic/scenario.yaml --out examples/synthetic
twinval run --data examples/synthetic/data --registry examples/synthetic/registry.yaml --config configs/synthetic.yaml --out my_results
twinval compare-truth --truth examples/synthetic/scenario_truth.csv --results my_results
```

## Data and privacy

`examples/synthetic` contains only simulated data (fictional instruments, no personal information). `examples/data` contains the answers of 484 real respondents and of their GPT-5 twins for BFI-2 and the Mental
Health Continuum. **Respondent identifiers were replaced by random codes** (`TW0001` ...); one mapping was applied to all files, so
respondents stay aligned across scales. No other personal information is included. If you use your own data, do not commit it.

## Caveats

* **Few instruments.** With the two example instruments cluster (per-instrument) bootstrap CIs, equal-instrument-weight
  statistics and leave-one-instrument-out analyses are degenerate. The framework then reports `NaN` intervals and adds a
  warning to `report.md`. Example results are illustrative and are **not** the study's results.
* **Harmonised categories at the item level.** When Human and Twin use different sets of response categories for an item
  (e.g. the twin never chooses "1"), threshold models cannot compare them, so rare categories are merged identically on both
  sides for CFA/ESEM. The item level uses the original answers; `item.data_version: harmonized` repeats it on the merged
  categories as a sensitivity analysis. Merged categories are re-numbered 1..k', so range-, extreme- and entropy-based
  metrics then refer to a coarser coding (`docs/METHODS.md`).
* **Order sensitivity of borderline CFA fits.** Weighted-least-squares fits of small, nearly saturated ordinal models (2-3 items) can converge or fail depending only on the *row order* of the data (floating point noise). In the original study several scales flipped between fits with different row orders; their structural status - and hence their type - can be fragile (in the example, the baseline of the BFI-2 facet *Creative Imagination* is nonconverged or not identified depending on the row order; it is not estimable in every order, so its status does not change; all scales of the Mental Health Continuum are stable). `twinval` sorts respondents by `ID` (deterministic) and, with `structural.order_check_permutations: N`, refits every candidate model on N random orders, writes `cfa_order_sensitivity.csv` and flags `cfa_order_sensitive` in `structural_scale_table.csv` when the baseline admissibility or the CFA conclusion changes.
* **Near-boundary twin estimates.** Twin-side standardised loadings are often close to 1 (in the full study >= .95 in 39 of 47 identified baselines, Human-side in none). These are flagged, not excluded; excluding them (`structural.exclude_near_boundary: true`) moves most scales to "model not estimable".
* **Tucker bootstrap** re-fits ESEM models in every replicate and is slow; it is resumable (`structural.resume`).
* Scale-level scores are computed from the *raw* items; harmonised items are used for the structural models (and, optionally, for the item level) - see [Data versions](#data-versions-raw-vs-harmonised).
